= Istio による仮想マシンのトラフィック管理

== はじめに

コンテナの世界において、Service Mesh（特に Istio）は最も望ましく変革的な Kubernetes 機能の一つとされています。
Service Mesh について語るとき、*モダン*、*12 Factor*、*SOA*、コンテナ化されたアプリケーションといった言葉とともに語られ、レガシーな仮想マシンと結びつけられることはありませんでした。

*UpLift and Shift* は、アプリケーションの書き換えやリプラットフォームを必要とせずに、追加の機能を提供することを目指しています。

Windows IIS で Web アプリケーションが動作しており、断続的なエラーやレイテンシーが報告されている状況を想像してください。
これらのレガシーな仮想マシンのトラブルシューティングにはどんなツールがあるでしょうか？

この最後のセクションでは、Istio と Kiali の高度なネットワークテレメトリを使って、レガシーな Windows 仮想マシンのこれらの問題を簡単にトラブルシューティングする方法を紹介します。

////

== Service と Route の削除

前のモジュールで作成した Service と Route はもう不要です。
Service Mesh がこれらの機能をはるかに堅牢なソリューションで置き換えます。

CAUTION: `windowsmesh-{user}` Namespace にいることを確認してください。

. OpenShift Console の左側で *Networking -> Services* をクリックし、見つかったすべての Service を削除します。
. Route を削除するには、*Networking -> Routes* をクリックし、見つかったすべての Route を削除します。

これで、これらの機能を Service Mesh に置き換える準備が整いました。

////

== VM で Service Mesh を有効化

. *各 winweb VM に移動* し、YAML の約 *175 行目* に `annotations:` セクションの一部として以下の行を追加します。
+
[source,yaml,subs="+attributes",role=execute]
----
  annotations:
        sidecar.istio.io/inject: "true"
        proxy.istio.io/config: |
          holdApplicationUntilProxyStarts: true
          proxyMetadata:
            ISTIO_META_DNS_CAPTURE: 'false'
            ISTIO_META_DNS_AUTO_ALLOCATE: 'false'
----

. *データベース VM に移動* し、YAML の約 *145 行目* に `annotations:` セクションの一部として以下の行を追加します。
+
[source,yaml,subs="+attributes",role=execute]
----
  sidecar.istio.io/inject: 'true'
----

== Namespace で Service Mesh を有効化

管理者は、あなたのユーザーに対して Namespace の Service Mesh を有効化する権限をすでに付与しています。
この設定方法に興味がある場合は、インストラクターにお尋ねください。

Namespace で Service Mesh を有効化するには

. *OpenShift Console の右上のプラス記号をクリック* します。
. 以下の YAML を貼り付けます。
+
[source,yaml,subs="+attributes",role=execute]
----
apiVersion: maistra.io/v1
kind: ServiceMeshMember
metadata:
  name: default
  namespace: windowsmesh-{user}
spec:
  controlPlaneRef:
    namespace: istio-system
    name: basic
----
+
. Istio サイドカーコンテナを起動するために、3 台すべての仮想マシンを再起動します。
.. *Virtualization -> VirtualMachines* をクリックし、`windowsmesh-{user}` Project にいることを確認します。
.. 各仮想マシンの右側にある拡張メニューを使って、それぞれを *Restart* します。
.. サイドカーコンテナが追加されたことを確認するには、*Workload -> Pods* に移動します。
Pod 内のコンテナ数が 2 になっているはずです。
2 つ目のコンテナが Service Mesh のサイドカーコンテナです。
+
NOTE: Windows 仮想マシンはグレースフルシャットダウンを行うため、再起動には 1〜2 分かかります。

[[getroute]]
=== Route の取得とテスト

DestinationRule はいくつかの要素でポリシーを定義します。
DestinationRule にはトラフィックの送信元を識別する `host` パラメーターがあります。
すでに作成されている Ingress Route をその値として使用します。

OpenShift Console を使って {user} の Route を見つけ、後で DestinationRule で使用するためにコピーします。

. *Networking -> Routes* をクリックし、*Project `istio-system`* が選択されていることを確認します。
. ユーザー名 `{user}` に一致する Route を特定します。
. コピーボタンで Route の Location をコピーします。
+
image::module-6-get-route.png[Route,link=self, window=blank, width=100%]
. *矢印をクリックしてアプリケーションにアクセス* します。
「Application is not available.」と表示されるはずです。
これは、Route がトラフィックを送信する Service がまだ構成されていないためです。
Kubernetes の Service を設定する代わりに、Service Mesh を設定しましょう！

[[visualizingtraffic]]
== トラフィックの可視化

負荷の可視化を支援するために、これらの仮想マシンと一緒に負荷生成ツールをデプロイしています。
実際のアプリケーションにトラフィックが来ている状態を再現するために、メッシュを通じてアプリケーションにトラフィックを送信します。
このアプリケーションが Service Mesh と Route を通じて公開されると、負荷生成ツールにより訪問者数が多く表示されます。

. 左側の *Graph* をクリックします。
. *Display* ドロップダウンボックスをクリックします。
.. *Response Time* にチェックを入れて、リクエストレイテンシーを確認します。
.. *Throughput* チェックボックスにチェックを入れて、データ転送レートを確認します。
.. *Traffic Distribution* チェックボックスにチェックを入れて、ロードバランシングの割合を確認します。
.. *Traffic Rate* チェックボックスにチェックを入れて、1 秒あたりのリクエスト数を確認します。
.. *Traffic Animation* チェックボックスにチェックを入れて、個々のリクエストを表す小さなドットを確認します。
+
.Kiali 詳細トラフィックグラフ
image::module-6-kiali-graph-setup.png[Kiali Graph Set Up,link=self, window=blank, width=100%]
+
. 右側のパネルに、リクエストのレスポンスコード（200、300、400、500 番台）が表示されることを確認します。

グラフをズームイン・ズームアウトして、トラフィックの詳細を確認してください。
